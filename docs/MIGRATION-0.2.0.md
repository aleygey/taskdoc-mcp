# 从 0.1.x 升级到 0.2.0

## 安装前

备份任务目录、看板和插件配置。关闭旧 TaskDoc / win-console 的写入入口，保留当前 `data.json` 和 SecretStorage 凭据，用 0.2.0 的三个发布文件覆盖旧插件后重载。

不要删除 `data.json` 再重新扫描来“重建”配置；其中包含已有任务引用的看板与列 ID。0.2.0 新增的 `runtime.json` 记录写入请求与恢复日志，后续迁移 Vault 时应一并保留。

## 数据迁移规则

| 数据 | 行为 |
| --- | --- |
| `checkpoint/v1` 活动任务 | 读取不修改；首次有效写入时升级为 v2，每项旧验收生成 `AC-1` 等 ID，初始待验证 |
| v1 已完成任务 | 保留历史完成状态；升级后标记 `legacy_acceptance_review`，不会假装旧 final evidence 已覆盖每一项验收 |
| v1 `archived` 状态 | 解释为 cancelled + archived；旧版本把结束与收起混在一起，无法推断实际完成验收 |
| v1 checkpoint / rich block | 保留原 ID、资料路径与内容；现有资料不批量改名 |
| 新任务文件 | UUID 文件名；改标题不改路径 |
| 现有按类型分列的看板 | 默认保留 type 模式，不自动重排列 |
| 看板列标题改名 | 在设置中“重连标题”，保持原 column ID |
| 普通笔记 / win-console 文档 | 不自动迁移或转换；查询报告异常链接，其他健康任务仍可用 |

历史已完成任务需要重新确认时，可打开验收窗口逐项关联旧证据并提交新验收；如果需要改范围或重做工作，先重新打开。重新打开会把任务验收重置为待验证，但保留已有子任务和任务级证据供复查。

## 客户端迁移

- 使用 `schema_version: 2`。版本 1 的字段形式仍可调用，验收语义已收紧，旧的“有一个完成子任务 + 一条 final evidence 就结束”逻辑需要更新。
- 简单任务不再要求 checkpoint。可直接创建 → 工作 → `task_finalize`。
- `task_finalize` 用 `acceptance` 指定验收项状态与证据引用；所有项满足后才能 done。豁免必须有理由。
- 新状态是 planned、active、blocked、done、cancelled。旧请求 `status: archived` 兼容解释为取消并归档，建议改用明确的 `status` 与 `archived`。
- `task_resume` 必须检查 `handoff_status`、`context_complete` 和活动核心省略标记。游标为当前结果的偏移；任务发生变更后应从首页重新读取。
- 手动卡片变更先 `task_reconcile` preview，再带两边 revision apply。手动打勾不能替代任务验收。
- 同一写请求重试保持 ID 和完整参数。`IO_BUSY` 可按错误动作重试；`VERSION_CONFLICT` 需重读；`RECOVERY_REQUIRED` 先处理诊断；`IDEMPOTENCY_EXPIRED` 表示该请求已经完成，不能换 ID 盲目重复创建。

## 升级后检查

1. 调用 `task_catalog`，确认看板和列 ID 没变。
2. 打开“查看任务诊断”，处理坏链接、改名列与卡片状态冲突。
3. 在测试任务上完成创建、编辑、验收、归档、重新打开流程。
4. 重载插件，以相同请求 ID 重试已成功的创建，确认没有新增第二个任务。
5. 再切换真实 AI 客户端。不要让新旧写入者同时操作同一组任务。

## 回退

旧插件不能写 `checkpoint/v2` 文档。若需回退，应关闭 0.2.0，恢复升级前的任务/看板/配置整体备份，再恢复旧插件文件。只覆盖旧 `main.js` 不是完整的数据回退方案。

## 人工正文冲突

编辑命令是日常修改入口。若直接修改了受管正文，恢复命令会展示原文与重建结果，应用时先备份整个原文件再重建。它不是文本合并器；请核对备份，将仍需保留的信息通过任务或子任务编辑器录入。

当崩溃日志与后来的人工作品冲突时，恢复会停止。保留 `runtime.json` 及相关文件副本，人工确认日志的 before/after 与当前内容后再处理；本版本不提供强制覆盖按钮。
